# Включение общего прогресса

Код приложения и SQL находятся в репозитории. Для работающей синхронизации нужен ваш проект Supabase: сам код не создаёт внешний аккаунт и не подменяет его демонстрационным сервером.

Подготовлены вход по email, необязательный пароль для других устройств, сохранение теории/задач/билетов/плана, локальная очередь, разрешение конфликтов и экспорт/импорт прогресса. Пока проект не подключён, приложение честно показывает локальный режим.

## 1. Создать проект Supabase

1. Откройте https://supabase.com/dashboard и создайте новый проект на бесплатном тарифе Free.
2. Название произвольное, например `discrete-study`. Пароль базы придумайте и сохраните у себя: приложению и разработчику он не нужен.
3. Дождитесь готовности проекта. В настройках подключения/API найдите **Project URL** и **Publishable key**. Для старых проектов вместо Publishable подходит публичный **anon key**.

**Не используйте `service_role`, `sb_secret_…` или пароль базы.** Публичный ключ предназначен для браузера; доступ к данным защищён входом и политиками базы. Приватные ключи не должны попадать в Vite, чат или GitHub. Если приватный ключ уже оказался в публичной сборке, перевыпустите его в Supabase.

## 2. Подготовить базу

В Supabase откройте **SQL Editor → New query**, вставьте весь файл:

[`supabase/migrations/202610250001_progress_sync.sql`](../supabase/migrations/202610250001_progress_sync.sql)

Нажмите **Run**. Скрипт создаёт таблицу с RLS и функцию синхронизации; его можно выполнить повторно. Auth-схема и роли в настоящем Supabase уже существуют — создавать их вручную не нужно. Тестовые схемы из `tests/` в проект не копируйте.

Каждый аккаунт видит только собственные строки. Запись идёт через функцию, которая определяет владельца по сессии, проверяет значения и серверные ревизии. Запрос не может указать чужого владельца.

## 3. Разрешить адрес сайта для входа

В **Authentication → URL Configuration** задайте адрес будущего сайта как **Site URL**:

```text
https://husteroflife67.github.io/colloquium-discrete-1module-hseami/
```

Это ожидаемый адрес после включения GitHub Pages, а не подтверждение, что сайт уже опубликован.

Добавьте этот же полный адрес в **Redirect URLs**. Для локальной разработки дополнительно разрешите `http://localhost:5173/` (и `http://127.0.0.1:5173/`, если открываете приложение так). Для собственного домена используйте его реальный адрес и корневой путь. Проверьте, что Email provider и создание новых пользователей включены.

## 4. Передать публичные настройки сборке

В GitHub откройте репозиторий → **Settings → Secrets and variables → Actions → Variables → New repository variable** и добавьте две переменные:

| Имя | Значение |
|---|---|
| `VITE_SUPABASE_URL` | Project URL из Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный Publishable key (или anon key) |

Это публичные настройки браузера, а не серверный секрет. Их значения будут в собранном JavaScript. Никакого административного ключа приложению не требуется.

Для локального запуска скопируйте `.env.example` в `.env.local`, заполните две переменные и перезапустите `npm run dev`. `.env.local` исключён из Git. Старый `VITE_SUPABASE_ANON_KEY` также поддерживается, но новая настройка Publishable имеет приоритет.

## 5. Опубликовать приложение

В репозитории откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**.

Затем **Actions → Build, test and publish study app → Run workflow**. Запуск вручную нужен также после изменения Variables: сами по себе новые значения не пересобирают уже опубликованный сайт.

Workflow устанавливает зависимости, выполняет тесты и проверку материалов, собирает сайт с правильным путём репозитория и публикует `dist`. PDF и изображения работают под тем же путём. После этого каждый push в `main` автоматически повторяет проверку и обновляет сайт. Если Pages ещё не включён, deploy завершится ошибкой настройки: включите Source как выше и повторите workflow; код и материалы от этого не теряются.

После успешного deploy откройте адрес из результата GitHub Actions. Внешняя публикация не считается проверенной только потому, что прошла локальная сборка.

## 6. Подключить три устройства

1. Откройте опубликованный сайт на ноутбуке → **Синхронизация**.
2. Если ранее занимались по другому адресу, сначала на старом адресе скачайте резервную копию, а на новом импортируйте её. Если адрес не изменился, старый `localStorage` будет использован автоматически.
3. Введите email и запросите ссылку для входа. Откройте письмо в браузере этого устройства. Первое письмо создаёт аккаунт, если его ещё нет.
4. После входа можно раскрыть **«Задать пароль для входа на других устройствах»** и задать пароль минимум из 8 символов.
5. На телефоне и планшете откройте тот же сайт → **Синхронизация → Email и пароль**. Войдите с тем же email и паролем. Можно также запрашивать отдельную ссылку для каждого устройства, но встроенная почта Supabase ограничивает частоту отправки; пароль не требует нового письма при каждом входе.
6. Дождитесь статуса **«Прогресс синхронизирован»**. Проверьте одну отметку плана или вопроса на втором устройстве.

Не создавайте три разных email-аккаунта: у них намеренно независимый прогресс. При забытом пароле можно снова войти через письмо и задать новый. Пароли и реальные ключи не нужно сообщать разработчику.

## Сохранение и конфликты

- Три прежних ключа `localStorage` сохраняются: основной курс, задачи и план. Отдельный `discrete-sync-v1` хранит очередь, владельца и последние серверные ревизии.
- Изменение отправляется примерно через 350 мс. Открытая страница проверяет обновления раз в 10 секунд, а также при возвращении в окно, восстановлении сети и по кнопке.
- Это синхронизация отдельных полей и билетов, а не замена всего прогресса одним JSON. Изменение вопроса на ноутбуке не удаляет галочку плана, добавленную с телефона. Ложная галочка хранится как `false`, поэтому снятие отметки тоже переносится.
- Разные независимо добавленные билеты объединяются по id. Одно повторно отправленное сохранение не создаёт дубликат.
- Одновременные разные изменения одного поля требуют выбора: **«Оставить на устройстве»** или **«Взять из аккаунта»**. До выбора локальная отметка сохраняется. Одинаковые значения объединяются без лишнего конфликта. Порядок определяется серверными ревизиями, а не часами устройств.
- В уже загруженном приложении без интернета можно менять отметки. Очередь хранится после перезагрузки; отправка продолжится после возврата сети и открытия приложения. Если закрыть устройство раньше отправки, откройте его снова, чтобы очередь дошла до сервера. Свежая загрузка сайта и ещё не загруженные PDF без сети не гарантируются: service worker не добавлялся.
- При выходе локальная копия остаётся. Её последующие изменения отправятся только при новом входе в тот же аккаунт. При смене аккаунта предыдущая копия сохраняется под отдельным ключом `discrete-account-<user_id>`; в другой аккаунт она автоматически не переносится.
- Экспорт содержит только три учебных раздела, без токенов входа. Импорт добавляет отсутствующие записи и не заменяет уже существующие локальные значения. Повторный импорт безопасен. Резервную копию можно перенести между адресами сайта и браузерами.
- Просмотр ответа не меняет знание или галочку. Черновики и незавершённые билеты не отправляются.

Если повреждён именно `discrete-sync-v1`, сначала экспортируйте прогресс. Не очищайте все данные браузера. Сохраните копию, выйдите и восстановите локальные отметки в новом профиле/чистом браузере через импорт, затем снова войдите: серверные конфликты будут предложены явно. При ошибке SQL или сети локальная копия не удаляется.

## Что проверено, а что требует настоящего проекта

- SQL-миграция выполняется в PostgreSQL WASM (PGlite): RLS, изоляция аккаунтов, запрет анонимного доступа, проверка данных, ревизии, повторные запросы и откат неверной пачки.
- В Chromium с перехваченным API проверяются два независимых браузерных контекста: объединение полей, три вида прогресса, обе истории билетов, офлайн-очередь, оба выбора конфликта, смена аккаунтов, вход, установка пароля и экспорт/импорт.
- Настоящая отправка писем, публичный домен Supabase, настройки redirect и публикация GitHub Pages могут быть проверены только после создания проекта, настройки переменных и успешного внешнего deploy. Подменённый тестовый API не означает, что облако пользователя уже подключено.

Команды:

```sh
npm ci
npm run build
npm test
node scripts/verify-materials.mjs
```

Тесты используют отдельный Vite на порту 5175 с заведомо тестовым проектом и перехватывают его запросы. Настоящие URL/ключи не нужны; тестовые пользовательские данные в реальный Supabase не отправляются.
